The harness in one page

Short answer

Nodes never call each other. A node finishes by leaving files in the ticket directory and a done record in state.json. The next node may start only when every token it requires has a done producer. S6 VERIFIED Everything a node receives comes through a driver-rendered packet, and everything it returns is a result file the controller records by digest. S15S16

  1. Two kinds of handoff. Control moves through tokens in state.json (driver-enforced). Data moves through artifact files such as plan.md (only their existence is checked). S6S18 VERIFIED
  2. The driver is the only writer of state. It replaces state.json atomically and appends every event to decisions.jsonl. S8S9 VERIFIED
  3. Reruns are surgical. Invalidating a node stales only the later nodes that consume its tokens. Reopening coding keeps the 2 test-case nodes. S4S29 VERIFIED
  4. 2 contracts have no machine check at all (graph node spec, facts JSON), and three exist only as conventions. See review points. VERIFIED
  5. Two real defects: a rerun node can pass with its old artifact, and the receipt ignores new untracked file contents. S18S10 VERIFIED
How to read this guide: §2 shows the actors and channels. §3–§4 answer "how does a node talk to the next one". §5–§7 give the shape of every contract. §8 maps every file on disk. §10 lists what to fix.

Who talks to whom

There are five actors. The controller (the main Claude session running SKILL.md) is the only one that talks to everybody. The driver (sdlc.py) owns state. Units are fresh subagents that each do one job and see only their packet. The user approves at fixed points. The files are the shared memory. S23

How one node hands work to the next

In one sentence: a node declares the tokens it requires and produces; the driver lets it run only when every required token has a producer whose record is done, and the actual content travels as files the producer wrote into the ticket directory.

Control: tokens

A token is an abstract name for "this kind of output exists and is approved", such as approved-plan. It is not a file. Several nodes may produce the same token: analysis comes from investigate on a bug and from requirement-analysis on a feature. That is how the two analysis branches merge into one implementation layer. S1

The readiness rule is: for each required token, find the nodes in this ticket's trace that produce it. If there are some and none is done, the node is not ready. A token that no node in the trace produces is ignored. This is how a family token (for example the IF proof) blocks final-review only when the family is on. S6S5 VERIFIED

Data: artifact files

Tokens say that a predecessor finished. What it found travels as files. coding reads plan.md, and code-review reads the diff plus plan.md. The packet names only the node's own output files and the ticket directory, so a unit finds its inputs by the naming convention in the node cards. S15S13 VERIFIED

Review point: inputs are implicit. The token table above already maps each token to its producer's files, so an inputs list per node could be generated and rendered into the packet (R3 in review points).

Going back: invalidation

When an earlier output is wrong, invalidate --node X (or a needs-changes gate, or triage-review --reopen X) walks forward from X. It collects every later node whose requires overlaps the tokens produced so far. Those nodes become stale with generation + 1. Every other node keeps its record. If final-review is among them, the receipts are dropped. S4S20 VERIFIED

What happens inside one node

Every node runs the same cycle: plan → packet → dispatch → result → record → gate. Only the controller calls the driver, and only the unit does the work. A node with a reviewer runs the dispatch–record part twice: workers first, then the reviewer over their results. S23

What the gate checks before a node is done

  1. Not already closed and ready: every required token has a done producer, otherwise G7 … not ready. S17
  2. Every planned unit has an ok record in the current generation; records from older generations do not count. S18
  3. The last reviewer verdict is not FAIL (nodes with a reviewer). S18
  4. Every artifact file exists. This is an existence check only: content and freshness are not checked (R1). S18
  5. User boundary: --actor user is required on user-boundary nodes; autoSkipPlanApproval relaxes it only on the two plan nodes. S18
  6. Side effects: pin the subject digest (subject nodes), issue receipts (final-review), verify receipts (deliverable-ready), record artifact digests, and apply --reopen (triage-review). S19
  7. Loop cap: needs-changes at attempt ≥ 2 raises G4 unless --actor user. S17

The rules files follow

  1. One writer per file. state.json and decisions.jsonl are written only by the driver. Artifacts are written only by their node's worker. Units never touch state. S8S9 VERIFIED
  2. Messages are immutable. Packet, rules and result names carry generation and round, so a rerun adds files and never overwrites. The unit record pins the result's sha256. S15S16 VERIFIED
  3. Artifacts are mutable. A rerun overwrites plan.md in place, and nothing archives the previous generation. The approved digest stays only in artifactDigests. S19 VERIFIED
  4. Nothing is deleted. Invalidation changes records, not files; the stale artifact stays on disk until the rerun overwrites it, which is the root of R1. S20 VERIFIED
  5. Review inputs are copied in. handback copies the exported review to reviews/round-N and logs its digest, so the ticket does not depend on the original file. S21 VERIFIED
  6. The repository is touched only by coding (mutability source). What ships from it is pinned by the subject digest and receipt. S2S10 VERIFIED
Suggested fix for mutable artifacts: on invalidate, move each stale node's artifacts to archive/g<N>/. The rerun must then recreate them, which closes R1, and you get a readable history per generation for free.

What to fix before relying on it

Found while reading the code for this guide on 2026-11-04. None of these is caught by the current 52 tests. S30

Review points, most severe first

IdSeverityProblemDetail and suggested fix
R1HighA rerun node can pass with the previous generation's artifactOn a reopen, artifact files stay on disk and the gate only checks is_file() S18. artifactDigests is recorded but never compared with the previous generation, so a worker that forgets to rewrite plan.md still passes. Fix: refuse approval when a stale node's artifact digest equals its last approved digest, unless the controller passes --unchanged-ok.
R2HighReceipt ignores the contents of new untracked filesThe subject digest hashes HEAD, git diff HEAD and only the names of untracked files S10. Editing a newly created (untracked) file after final-review does not break the receipt. Fix: hash each untracked file's content, or git add -N the intended paths first.
R3MediumNode inputs are implicitA token says a predecessor is done, but the packet lists only the node's own outputs S15. A unit finds plan.md or investigation.md by convention. Fix: derive an inputs list per node (token → producer's artifacts, see the token table) and render it into the packet.
R4MediumArtifact shape is prose-onlyRequired sections (## Confirmed cause, ## Condition → negative case, ## Rule self-check) live in node cards; the gate does not parse them. Fix: add requiredSections to node specs and check headings at the gate.
R5MediumNo schema for graph/lifecycle.json, facts JSON or decision eventsThree of the contracts exist only as conventions; a typo in a graph key is silently ignored. Fix: add graph.schema.json, facts.schema.json, decision-event.schema.json and validate on load.
R6MediumProfile validation is lighter than the schemaThe schema says additionalProperties: false, but the built-in check does not enforce it S24. Fix: validate with jsonschema when available, fall back to the light check.
R7LowRead commands write statestatus and plan call save() S14 to add records for nodes that newly entered the trace. Harmless today, but it makes a read a write. Fix: add missing records only in handback/init.
R8LowDecision log is not tamper-evidentdecisions.jsonl is append-only by convention and never read back S9. Fix: add prevDigest per line (hash chain) and verify it in status.
Suggested order: R1 and R2 first (they let wrong work pass a gate), then R3 and R4 (they make the node-to-node data contract explicit), then the schema work in R5–R6.
