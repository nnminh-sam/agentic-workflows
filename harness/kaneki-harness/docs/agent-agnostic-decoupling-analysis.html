Decoupling Kaneki Harness from Claude Code

A complete codebase audit identifying every Claude Code-specific dependency in kaneki-harness, separating the already-agnostic SDLC core from the coupled host shell, and defining a clean porting blueprint for multi-agent portability (Codex CLI, Gemini CLI, OpenCode, Cursor, Antigravity, and headless runners).

Deep-Dive Analysis of Coupling Surfaces

1. Skill Packaging, Installation Layout & Environment Variables

CRITICAL Medium Effort

Today, sdlc install assumes the target agent is Claude Code. It copies skills into <target>/.claude/skills/<name>/, copies agents into <target>/.claude/agents/, writes <target>/.claude/kaneki-harness.json, and instructs the user to restart Claude Code. Inside every SKILL.md, the controller constructs the driver command using Claude-only environment variables: 

SDLC="sh $CLAUDE_SKILL_DIR/scripts/sdlc"   # skills/kaneki-flow/SKILL.md:28, onboarding:15, ship:17

Additionally, the YAML frontmatter in all three SKILL.md files uses Claude Code extensions (when_to_use, argument-hint, user-invocable, and hooks.PreToolUse). On Codex CLI, Gemini CLI, Cursor, or OpenCode, $CLAUDE_SKILL_DIR is empty, causing every $SDLC command to fail immediately.

Why It Breaks on Other Agents

  • Other agents discover instructions in different roots (.agents/skills/, .codex/, .gemini/, .cursor/rules/, AGENTS.md).
  • $CLAUDE_SKILL_DIR and $CLAUDE_PROJECT_DIR are never exported outside Claude Code.
  • Slash command invocation (/kaneki-flow ISSUE-123) varies by host syntax or may not exist in headless CLI agents.

Decoupling Strategy

  • Install a stable, host-agnostic driver shim into .sdlc/bin/sdlc (or global ~/.local/bin/kaneki-sdlc) so skills simply call sdlc or sh .sdlc/bin/sdlc without env vars.
  • Refactor harness/install.py into host emitters: sdlc install --target . --host claude|codex|gemini|cursor|opencode|generic.
  • Keep canonical Markdown playbooks under playbooks/ (neutral frontmatter) and let each host emitter wrap them in that host's required directory & frontmatter format.

2. Git Guard Enforcement (PreToolUse Hook)

CRITICAL High Effort

Kaneki enforces a strict safety invariant: nodes never commit, push, rebase, or delete work. Currently this is enforced proactively via a Claude Code PreToolUse hook declared inline in skills/kaneki-flow/SKILL.md:7–15: 

hooks:
  PreToolUse:
    - matcher: "Bash|PowerShell"
      hooks:
        - type: command
          command: 'g=".claude/skills/kaneki-flow/scripts/guard-git"; d="${CLAUDE_PROJECT_DIR}"; ...'

guard_git.py reads Claude Code's hook payload from stdin (data["tool_input"]["command"], data["cwd"]), resolves .claude/kaneki-ship-approvals.json, and returns exit code 2 to block execution.

Why It Breaks on Other Agents

  • Many agents (Codex CLI, Aider, OpenCode, generic LLM loops) do not support Claude's PreToolUse hook schema or exit-code-2 blocking semantics.
  • Agents that do support hooks (e.g., Gemini CLI, Cursor) use different JSON payload schemas and config locations.
  • Approval state is stored in .claude/kaneki-ship-approvals.json, tying ship state to a Claude directory.

Decoupling Strategy (Defense in Depth)

  • Relocate state: Move approvals to .sdlc/ship-approvals.json (harness-owned).
  • Layer 1 — Git Hooks (100% Agent-Agnostic): During sdlc worktree / init, install lightweight pre-commit and pre-push hooks inside the ticket worktree's git dir that check .sdlc/ship-approvals.json. Works for every agent and shell!
  • Layer 2 — Host Tool Hooks (Optional Adapter): Extract the pure command parser in guard_git.py into a library, and provide thin stdin/stdout shims per host that supports pre-tool hooks (Claude, Gemini CLI, etc.).
  • Layer 3 — Post-hoc Gate Audit (Already Agnostic): Keep _commit_rule_problem() in cli.py:633, which already rejects unauthorized commits at gate time regardless of agent.

3. Hard Dependency on the my-git Claude Code Plugin

CRITICAL High Effort

As of 2026-11-19, kaneki-ship delegates all git commit/push/PR operations to the external my-git Claude Code plugin. This creates four hard coupling points:

  • harness/mygit.py:34–47 — require_root() fails closed (G7) unless plugins/my-git/.claude-plugin/plugin.json exists.
  • harness/install.py:44, 73–74 & mygit.py:91–122 — executes my-git/install.py and mutates .claude/settings.json and .claude/settings.local.json (extraKnownMarketplaces, enabledPlugins).
  • harness/ship.py:97 — invokes my-git/scripts/check_message.py via subprocess to validate Conventional Commits / no-AI-attribution rules.
  • harness/ship.py:158–163, skills/kaneki-ship/SKILL.md:43–48, and adapters/delivery/github-pr.json:27–36 — emit Claude slash commands (/my-git:commit, /my-git:push, /my-git:pr) as the required next steps.

Why It Breaks on Other Agents

  • .claude-plugin/plugin.json and extraKnownMarketplaces are Claude Code marketplace primitives.
  • Non-Claude agents cannot execute /my-git:commit, /my-git:push, or /my-git:pr slash commands.
  • Users without the sibling plugins/my-git checkout cannot even run sdlc install or sdlc ship-request.

Decoupling Strategy

  • Introduce a pluggable delivery.ship.backend setting in the profile/delivery adapter:
    • native-git (default for agent-agnostic): sdlc ship --approve <digest> commits via harness/gitid.py (already applies GIT_AUTHOR_*, GIT_COMMITTER_*, GIT_SSH_COMMAND!), pushes, and opens PRs via gh/glab or prints a compare URL.
    • my-git (optional Claude Code adapter): retains the current staging + /my-git:* handoff when running on Claude Code.
  • Port the Conventional Commits / no-AI-coauthor check into harness/checks.py (stdlib Python, ~40 LOC) so ship-request needs no external plugin script.
  • Make my-git registration in install.py conditional on --host claude --with-my-git.

4. Subagent Dispatch, Agent Definitions & Token Reporting

HIGH High Effort

Kaneki's quality model relies heavily on fresh, isolated subagents (workers and independent reviewers that see only their rendered packet, never the controller's chat history). Today, this is wired directly to Claude Code's custom subagent system:

  • skills/kaneki-flow/agents/kaneki-{light,worker,deep}.md define Claude subagents with YAML frontmatter (model: haiku|sonnet|opus, tools: Read, Grep, Glob, Bash, Write, Edit, autoCompactWindow: 200000).
  • Critical insight: kaneki-deep.md contains the valuable 5-step adversarial reasoning card (Floor check → Hypotheses → Simulate concretely → Attack weakest claim → Calibrate). Because it lives inside a Claude agent file rather than the packet, any non-Claude runner would lose it!
  • harness/cli.py:330 hardcodes AGENT_TYPES = {"light": "kaneki-light", "routine": "kaneki-worker", "deep": "kaneki-deep"} and returns agentType in plan and packet.
  • SKILL.md:142 expects the controller to read total tokens from Claude Code's subagent completion notice and pass --tokens <n> to sdlc record.

Why It Breaks on Other Agents

  • Agents like Aider, Cursor (standard chat), and older CLI loops have no native subagent spawning tool.
  • Agents that do have subagents (Codex, Gemini CLI, OpenCode, Antigravity) use different spawn APIs, model flags, and do not read .claude/agents/*.md.
  • Many agents do not expose subagent token counts in a completion notice.

Decoupling Strategy

  • Move role protocols into packets: Move the body of kaneki-light.md, kaneki-worker.md, and kaneki-deep.md (especially the deep reasoning card) into neutral roles/{light,routine,deep}.md files and inline or link them directly in packet-template.md.
  • Three execution modes via a Runner Adapter:
    1. Host-native subagents (Claude Code, Antigravity, OpenCode): host adapter maps logical tier → native subagent call.
    2. External CLI subprocess runner (sdlc dispatch --ticket T --node N --unit U): spawns a fresh headless CLI process (codex exec, gemini -p, claude -p, opencode run) with the packet path, captures stdout/usage JSON, and optionally auto-calls sdlc record!
    3. Manual / Handoff mode: prints the packet path for a human or external orchestrator to run in a fresh session.
  • Rename agentType in CLI output (or add roleProfile alongside it for backward compatibility with CONTRACT_VERSION = 1).

5. Interactive User Prompts (AskUserQuestion) & Tool Naming

HIGH Low Effort

Several prompt files call Claude Code's built-in tools by exact name:

  • AskUserQuestion appears in skills/kaneki-flow/SKILL.md:149, skills/kaneki-onboarding/SKILL.md:45, skills/kaneki-ship/SKILL.md:35, and skills/kaneki-flow/references/nodes/scope.md:16.
  • Read, Grep, Glob, Bash, PowerShell appear in packet-template.md:45–47, scope.md:7, and agents/*.md.

Why It Breaks on Other Agents

Other agents either lack a structured question tool (they ask in plain chat text) or name it differently (e.g., ask_question, request_user_input). Strict instruction-following models may stall or error looking for a nonexistent tool named AskUserQuestion.

Decoupling Strategy

Replace concrete tool names with capability-level instructions in canonical playbooks and packets:

  • "Ask the user (using your host's structured question UI if available, otherwise numbered options in chat; ≤ 4 questions at a time, recommended option first)."
  • "Search with line numbers first, then read targeted line ranges."

6. Model Tier Defaults & Design System Naming

MEDIUM Low Effort

Notably, the Python driver is already model-name-agnostic: harness/profile.py and harness/cli.py treat models.light, models.routine, and models.deep as opaque strings. However, Claude model names leak in three places:

  • harness/onboard.py:687–688 hardcodes fallback defaults ("models.routine", "sonnet") and ("models.deep", "opus").
  • skills/kaneki-flow/agents/*.md hardcode model: haiku / sonnet / opus in frontmatter.
  • app/design-system/tokens.json:38–46 and app/doc/design-system.html name CSS/JS color tokens haiku, sonnet, opus (and soft/text variants) rather than tier names.

Impact

A user running OpenAI (gpt-5-mini / o3) or Gemini (gemini-2.5-flash / gemini-2.5-pro) gets invalid Claude model defaults on onboarding and misleading CSS class names in the desktop UI.

Decoupling Strategy

  • Add a provider / model preset question in onboard.py (Claude, OpenAI/Codex, Gemini, Custom) or let the host adapter supply default tier-to-model mappings.
  • Rename design tokens from haiku/sonnet/opus to tier-light/tier-routine/tier-deep (with optional deprecated aliases).

7. Planned Desktop App (app/ & docs/desktop-app/plan.md)

PLANNED / SPEC High Impact if Built As-Is

The Go + Wails desktop app is currently in the planning stage (no Go code yet), which makes this the ideal moment to decouple its design before implementation starts. Four design decisions in plan.md and app/doc/build-plan/parts/P6–P8 are Claude-specific:

  • D5 / P6 (Session Supervision): Spawns claude -n kaneki-<ticket>-<node> --session-id <uuid> --permission-mode acceptEdits --append-system-prompt-file ....
  • Q1 / P6 (Live Status & Permission Waiting): Injects a Claude Code Notification / Stop / SessionStart hook writing to runs/<id>/events.jsonl.
  • D7 / P7 (Real Cost Panel): Parses Claude Code's private transcript format at ~/.claude/projects/<cwd-slug>/<session>.jsonl and <session>/subagents/*.jsonl.
  • P8 (Environment Probe & Onboarding): Probes for the claude binary and hands off weak-repo interpretation / --refresh to a Claude session.

Decoupling Strategy (Before Writing Go Code)

Define a clean Go interface in the Wails Host (host/agent/backend.go) so the UI and ticket supervisor never know which CLI agent is running:

type AgentBackend interface {
    ID() string                                          // "claude-code", "codex-cli", "gemini-cli", "opencode"
    Probe(ctx context.Context) EnvProbeResult            // binary path, version, capabilities
    BuildLaunchCmd(req LaunchRequest) (*exec.Cmd, error) // args, system prompt, env, hook config
    WatchSessionEvents(runDir string) (<-chan SessionEvent, error)
    ParseUsage(workspace string, since time.Time) ([]UsageRecord, error)
}

Phased Migration Roadmap

Execute in four incremental phases. After each phase, the existing Python test suite (python3 -m unittest discover -s tests -v) must stay 100% green, and Claude Code compatibility remains unbroken as the first host adapter.

Phase 1 — Decouple Ship & Git Safety (Removes the 2 Hardest Blockers)
Goal: Any agent can run the full lifecycle including kaneki-ship without my-git or Claude hooks.
  • Port Conventional Commits + no-AI-attribution check into harness/checks.py (remove hard subprocess call to my-git/scripts/check_message.py).
  • Add native-git ship backend in harness/ship.py using gitid.run() + optional gh/glab CLI; keep my-git as an opt-in backend.
  • Move ship approvals from .claude/kaneki-ship-approvals.json to .sdlc/ship-approvals.json.
  • Install worktree-level git pre-commit / pre-push hooks during sdlc worktree / init for universal, agent-agnostic history protection.
Phase 2 — Neutralize Prompts, Role Cards & Packets
Goal: Zero Claude-specific tool names, env vars, or model names in canonical playbooks and packets.
  • Extract roles/{light,routine,deep}.md from skills/kaneki-flow/agents/*.md and embed the role card (especially deep's 5-step adversarial reasoning protocol) directly into rendered packets in cmd_packet().
  • Replace AskUserQuestion and Claude tool names (Read, Grep, etc.) in SKILL.md, scope.md, and packet-template.md with capability-based phrasing.
  • Replace $CLAUDE_SKILL_DIR/scripts/sdlc with a workspace-local shim .sdlc/bin/sdlc (or PATH binary).
  • Add model preset selection to harness/onboard.py instead of hardcoding sonnet/opus.
Phase 3 — Multi-Host Installer & External Subagent Runner
Goal: One-command install and subagent execution on Claude Code, Codex CLI, Gemini CLI, Cursor, and OpenCode.
  • Refactor harness/install.py to support --host claude|codex|gemini|cursor|opencode|generic via hosts/ emitters.
  • Keep --host claude generating the exact .claude/ structure + PreToolUse hook shim for backward compatibility.
  • Add harness/dispatch.py (sdlc dispatch --ticket T --node N --unit U --runner <cmd>) so agents without native subagents (or headless CI) can spawn fresh worker/reviewer processes per unit and capture token counts automatically.
Phase 4 — Align Desktop App Spec & Design System Before Coding
Goal: Prevent Claude Code lock-in from re-entering via the upcoming Go/Wails desktop app.
  • Update app/design-system/tokens.json to rename haiku/sonnet/opus tokens to tier-light/tier-routine/tier-deep.
  • Update docs/desktop-app/plan.md (D5, D7, Q1) and P6–P8 specs to define the Go AgentBackend interface (session launch, event watcher, usage log parser) with ClaudeCodeBackend as adapter #1.
  • Generalize harness/web_page.html ("Open in Editor" instead of hardcoded "Open in Zed").
