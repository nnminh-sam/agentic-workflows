Coupling Surfaces (1–8)

1. Skill Packaging, Installation Layout & Environment Variables

CRITICAL Phase 3 Target · Medium Effort

Today, sdlc install assumes the target agent is Claude Code. It copies skills into <target>/.claude/skills/<name>/, copies agents into <target>/.claude/agents/, writes <target>/.claude/kaneki-harness.json, and instructs the user to restart Claude Code. Inside every SKILL.md, the controller constructs the driver command using Claude-only environment variables: 

SDLC="sh $CLAUDE_SKILL_DIR/scripts/sdlc"   # skills/kaneki-flow/SKILL.md:28, onboarding:15, ship:22

Additionally, the YAML frontmatter in all three SKILL.md files uses Claude Code extensions (when_to_use, argument-hint, user-invocable, and hooks.PreToolUse). On Antigravity, Codex CLI, Gemini CLI, Cursor, or OpenCode, $CLAUDE_SKILL_DIR is empty, causing every $SDLC command to fail immediately.

Why It Breaks on Other Agents

  • Other agents discover skills/rules in different roots (.agents/skills/, .gemini/antigravity/, .codex/, .cursor/rules/, AGENTS.md).
  • $CLAUDE_SKILL_DIR and $CLAUDE_PROJECT_DIR are never exported outside Claude Code.
  • Slash command invocation (/kaneki-flow ISSUE-123) varies by host syntax or may not exist in headless CLI agents.

Decoupling Strategy

  • Install a stable, host-agnostic driver shim into .sdlc/bin/sdlc (and optional global PATH) so playbooks simply invoke sh .sdlc/bin/sdlc with zero env vars.
  • Refactor harness/install.py into host emitters: sdlc install --target . --host antigravity|claude|codex|gemini|cursor|opencode|generic.
  • Store canonical Markdown playbooks under playbooks/ and let each host emitter prepend its Tool Binding Preamble and host-native frontmatter.

2. Git Guard Enforcement (PreToolUse Hook → Worktree Git Hooks)

PHASE 1 DONE (CORE) Phase 3: Host Tool Hook Shim

Kaneki enforces a strict safety invariant: nodes never commit, push, rebase, or delete work. Originally this relied on Claude Code's PreToolUse shell hook in skills/kaneki-flow/SKILL.md:7–15 and .claude/kaneki-ship-approvals.json.

Completed in Phase 1 (d7e3914)

  • Harness-owned approvals: Created harness/approvals.py storing short-lived approvals in .sdlc/ship-approvals.json (with legacy read/revoke fallback for .claude/kaneki-ship-approvals.json).
  • Agent-agnostic git hooks: Created harness/worktree_hooks.py, wired into cmd_worktree(), installing isolated pre-commit and pre-push hooks on linked ticket worktrees via extensions.worktreeConfig + --worktree core.hooksPath (chaining pre-existing repo hooks with </dev/null stdin preservation).
  • Guard fallback: Updated guard_git.py (stdlib-only) to read .sdlc/ship-approvals.json first.

Remaining for Phase 3

  • Worktree hooks block unauthorized commit and push for every agent and shell; post-hoc _commit_rule_problem() audits history at gate time.
  • For hosts that support pre-tool shell interception (Claude PreToolUse, Gemini CLI BeforeTool) to also catch destructive worktree operations (reset --hard, clean -f) before execution, emit host-specific hook shims in hosts/<host>/ while keeping the command parser shared.

4. Subagent Dispatch, Agent Definitions & Token Reporting

HIGH Phase 2–3 Target

Kaneki's quality model relies on fresh, isolated subagents (workers and independent reviewers that see only their rendered packet, never the controller's chat history). Today, this is wired directly to Claude Code's custom subagent system:

  • skills/kaneki-flow/agents/kaneki-{light,worker,deep}.md define Claude subagents with YAML frontmatter (model: haiku|sonnet|opus, tools: Read, Grep, Glob, Bash, Write, Edit, autoCompactWindow: 200000).
  • Critical trap: kaneki-deep.md contains the 5-step adversarial reasoning card (Floor check → Hypotheses → Simulate concretely → Attack weakest claim → Calibrate). Because it lives inside a Claude agent file rather than the packet, any non-Claude runner loses it!
  • harness/cli.py:330 hardcodes AGENT_TYPES = {"light": "kaneki-light", "routine": "kaneki-worker", "deep": "kaneki-deep"} and returns agentType in plan and packet.
  • SKILL.md:142 expects total tokens from Claude Code's completion notice for --tokens <n>.

Decoupling Strategy

  • Inline role cards in packets: Move role instructions (especially deep's 5-step adversarial card) into playbooks/roles/{light,routine,deep}.md and embed them directly in cmd_packet().
  • Host dispatch + fallback runner: Use each host's native subagent tool (see Deep-Dive B) or sdlc dispatch headless CLI subprocess runner (codex exec, gemini -p, claude -p) when a host lacks subagents or cross-agent routing is requested.

Token Accounting Resilience

  • Hosts like Claude Code and headless CLI runners (`codex exec --json`, `gemini --output-format json`) return token counts; hosts like Antigravity's `invoke_subagent` may not expose subagent tokens directly to the parent controller.
  • Allow --tokens to remain optional (already supported by usage.py, which marks missing rounds as unreported) and capture tokens automatically whenever sdlc dispatch runs a subprocess.

Deep-Dive A: Per-Node & Per-Agent Model Configuration

In the current codebase, graph/lifecycle.json assigns every unit a capability tier (light, routine, or deep, plus optional escalate), and sdlc.profile.json maps those three tiers to opaque strings in models.{light,routine,deep} (harness/profile.py:68–82). In practice, porting to Antigravity, Codex, Gemini, and mixed-agent setups breaks this flat model map in five ways:

Trap 1 · Shared Repo Config vs. Developer Host sdlc.profile.json is project config (often committed/shared), yet Alice runs Claude Code (sonnet/opus), Bob runs Antigravity (flash/pro), and CI runs Codex CLI (gpt-5.2-codex). Hardcoding concrete model names in sdlc.profile.json breaks portability across contributors.
Trap 2 · Model Is Not Always a Free-Form String Different agents parameterize capability differently: Claude uses model aliases/IDs; Codex pairs model + reasoning_effort (low|medium|high); Antigravity's invoke_subagent only accepts a fixed 4-value enum (inherit|flash_lite|flash|pro), while swarm accepts display model names; some IDE hosts only allow inherit.
Trap 3 · Static Agent Frontmatter Conflict skills/kaneki-flow/agents/kaneki-light.md hardcodes model: haiku, kaneki-worker.md hardcodes sonnet, and kaneki-deep.md hardcodes opus — directly contradicting profiles that omit models.light (fallback to routine) or escalate coding after 2 fails.
Trap 4 · Rigid cmd_record() Equality Check harness/cli.py:532 enforces if args.model != s.model(tier): raise HarnessError(...). This breaks when a host reports a resolved versioned model ID (claude-sonnet-4-6 vs sonnet), runs an inherit-only subagent, or uses a host-native tier enum (pro vs gemini-2.5-pro).
Trap 5 · Context Window Is Host-Bound profile.contextWindow defaults to 200_000 globally, even though actual limits vary per active host and model (e.g. Gemini 1M vs Claude 200k vs smaller local/fast models) and directly drive cmd_packet()'s 25% warning threshold.

Deep-Dive B: Orchestrator Tool-Triggering & User Interaction Protocol

Kaneki's controller (SKILL.md) is a prompt-driven orchestrator running inside whatever AI host the user opened. Currently, the playbooks mix SDLC workflow logic with Claude-specific tool-calling syntax, and even worse, Claude Code's UI constraints leaked into Python driver output:

Hidden Coupling Discovered in harness/onboard.py & Prompt Files
  • harness/onboard.py:558 slices tracker options to opts[:4], :611 slices compose DBs to [:3] + None, and :660 slices git identities to ident_cands[:3] — purely to fit Claude Code's 4-option limit in AskUserQuestion.
  • skills/kaneki-flow/SKILL.md:149, kaneki-onboarding/SKILL.md:45, and scope.md:16 instruct the LLM to call AskUserQuestion (≤ 4 per call), and packet-template.md:45–47 mandates Claude tool names Grep and Read.
  • Why this fails on Antigravity (and others): Antigravity's ask_question uses plain string options with a "(Recommended)" prefix (not {label, description} objects), auto-adds numbering & "Other", and explicitly instructs the model NOT to use it for trivial yes/no questions (plain text instead). Meanwhile, Antigravity spawns subagents via invoke_subagent(TypeName="self", Model="...", Role="...", Prompt="...") and resumes them with send_message(Recipient=conversationId, ...).

Clean Solution: Canonical 5-Intent Playbooks + Thin Host Tool Binding Preambles

Instead of maintaining 6 diverging copies of the 200-line workflow, keep one canonical playbook set under playbooks/ written purely in terms of 5 abstract orchestrator intents. At install time, sdlc install --host <host> prepends a tiny (~20–30 line) Host Tool Binding Preamble so the host LLM gets unambiguous, exact tool names without duplicating SDLC rules.

## Dispatch & Doubts
1. Run `DRIVER_CALL`: `sdlc packet --ticket <id> --node <n> --unit <u> --facts <f>`.
2. Execute `DISPATCH_UNIT` using the `execution` block from the packet JSON
   with the one-line prompt:
   "Read the packet at <path> (sha256 <packetDigest>) and execute it."
   (Packets with disjoint outputs may be dispatched in parallel.)
3. On reviewer FAIL (`artifact`-class): build a round-2 packet with
   `findingsToFix` and run `RESUME_UNIT` (or fresh `DISPATCH_UNIT`).
4. Classify doubts into HIGH and LOW. Ask HIGH doubts via `ASK_USER`
   (recommended option first, evidence in artifact, no paths in question).

## Host Tool Binding (Antigravity)
- `DRIVER_CALL`: run `sh .sdlc/bin/sdlc ...` via `run_command`.
- `DISPATCH_UNIT`:
  - If `execution.dispatchMode == "native"`: call `invoke_subagent` with
    `TypeName="self"`, `Model=<execution.model>` (inherit|flash_lite|flash|pro),
    `Role="<node> <unit>"`, `Prompt=<one-line packet prompt>`.
  - If `execution.dispatchMode == "subprocess"`: call `sdlc dispatch ...` via `run_command`.
- `RESUME_UNIT`: call `send_message(Recipient=<conversationId>, Message=<round-2 packet>)`,
  or call `invoke_subagent` fresh if no session is alive.
- `ASK_USER`: use `ask_question` for multi-option choices (prefix first option with
  `(Recommended)`), and plain chat text for simple Yes/No confirmations.
