The harness in one page

Short answer

Nodes never call each other. A node finishes by leaving files in the ticket directory and a done record in state.json; the next node may start only when every token it requires has a done producer. Who talks to whom

There are five actors. The controller (the main Claude session running SKILL.md) is the only one that talks to everybody. The driver (sdlc.py → harness/) owns state. Units are fresh subagents that each do one job, see only their packet, and run on the tier the plan names. The user approves at fixed points. The files are the shared memory. In the lite lane the controller also does a few nodes itself (inline), with no unit. S21S22

How one node hands work to the next

In one sentence: a node declares the tokens it requires and produces; the driver lets it run only when every required token has a producer whose record is done, and the actual content travels as files the producer wrote into the ticket directory, which the packet now names as the node's inputs.

Control: tokens

A token is an abstract name for "this kind of output exists and is approved", such as approved-plan. It is not a file. Several nodes may produce the same token: analysis comes from investigate on a bug, from requirement-analysis on a feature, and from scope in the lite lane. That is how different branches merge into one implementation layer. S25

The readiness rule is: for each required token, find the nodes in this ticket's trace that produce it. If there are some and none is done, the node is not ready. A token that no node in the trace produces is ignored. This is how a family token (for example the IF proof) blocks final-review only when the family is on. S1S26 VERIFIED

Data: artifact files, now listed as inputs

Tokens say that a predecessor finished. What it found travels as files. The driver now derives each node's inputs: for every token the node requires, it takes the artifacts of the settled node that produced it. plan prints them, and packet renders them into the packet with their sha256. S7S29 VERIFIED

An input whose text carries superseded rounds or a token-usage block is handed over as a live-only copy under packets/<dispatch>.inputs/; the original file stays the record. S30S31 VERIFIED

Fixed (was R3)Inputs used to be implicit: a unit found plan.md by naming convention. They are now generated from the token graph and pinned by digest in the packet.

Going back: invalidation

When an earlier output is wrong, invalidate --node X (or a needs-changes gate, or triage-review --reopen X) walks forward from X. It collects every later node whose requires overlaps the tokens produced so far. Those nodes become stale with generation + 1, and each of their markdown artifacts gets a ## SUPERSEDED: <date> — rerun from X (generation N) invalidated this artifact line. Every other node keeps its record. If a receipt-issuing node is among them, the receipts are dropped. S15S16 VERIFIED

Fixed (was R1)A rerun node can no longer pass with its old artifact: the gate reads only the text below the last ## SUPERSEDED: line and refuses an artifact whose live part is empty. S33S17

Two lanes: full and lite

A lane picks the trace. full (the default) runs the whole graph in a per-ticket worktree. lite replaces the main order with its own short one and works in the repository checkout itself, for changes that are small and already understood. S4S34 VERIFIED

Choosing and changing the lane

  1. init --lane full|lite records the lane in the ticket context (missing = full, for tickets created before lanes). A lane other than full with families is refused. The worktree-root check runs only for lanes that use worktrees. S36S38
  2. In-place binding. For an inPlace lane, init binds each repository's worktree to its own checkout and warns when the checkout has uncommitted changes or sits on the base branch. S37
  3. Inline nodes. For a node listed in the lane's inline, the driver drops its units and reviewer, so plan says executor: controller and the gate needs no unit record. scope and change have no units in the graph at all. S22S29
  4. Escalation: sdlc lane --set full --reason …. Closed nodes keep their records (they are just no longer in the trace); the new lane's nodes that never ran become pending, so the next node is prepare. The repositories stay bound to their current checkout. The skill forbids moving full → lite to skip work. S11S39S40

What happens inside one node

Every node with units runs the same cycle: plan → packet → dispatch → result → record → gate. Only the controller calls the driver, and only the unit does the work. A node with a reviewer, or with staged units, runs the dispatch–record part more than once. An inline node (lite lane) skips dispatch: the controller writes the artifacts from the node card and closes the gate. S21S22

Node record states

What the gate checks before a node is done

  1. Not already closed and ready: every required token has a done producer, otherwise G7 … not ready. S42
  2. Every planned unit has an ok record in the current generation, the reviewer included; records from older generations do not count, and an inline node plans none. S33
  3. The last reviewer verdict is not FAIL (nodes with a reviewer). S33
  4. Every artifact exists and has live text. A markdown artifact whose text below the last ## SUPERSEDED: line is empty is refused as "not rewritten". S33S43
  5. Declared checks pass on the live text: required sections and the parsers confidence, conditions, design-rules, rule-self-check, rule-verdicts, verdict, reopen. These also run on needs-changes, where the artifact's verdict must say NEEDS CHANGES. S6S42
  6. Citations resolve. Every backticked path:line must name an existing file with that many lines; broken ones block a subject node and are a warning elsewhere. S44S33
  7. Language of drafts and PR replies matches the configured one, otherwise G5 unless --actor user. S45
  8. User boundary: --actor user is required on user-boundary nodes; autoSkipPlanApproval relaxes it only on the two plan nodes. S45
  9. Commit rule on subject and receipt-checking nodes: no commit since the ticket started except those kaneki-ship made, and none authored as anyone but the project identity. S46
  10. Side effects: pin the subject digest, issue or verify receipts, append the ## Token usage block, record artifact digests, apply --reopen, then rewrite token-usage.md. S47S48
  11. Loop cap: needs-changes at attempt ≥ cap (default 2) raises G4 unless --actor user. S42

Which model runs each unit

Units name a tier, never a model. The profile maps models.light, models.routine and models.deep to model names; light is optional and falls back to routine. Each tier has its own agent type. S5S49S50 VERIFIED

Staged units

A unit with after: <unit> may run only once that unit recorded PASS (or APPROVED) with status ok at the current generation. Both packet and record refuse it otherwise, and a predecessor recorded without a verdict must be re-recorded. When the technical review fails, the controller closes code-review with needs-changes at once. S53S54 VERIFIED

Escalation

A unit with escalate: {tier, afterFails, reviewNode} runs on the stronger tier once its review node has afterFails generations that contain a FAIL or NEEDS CHANGES record. plan shows escalated: {from, why}, packet renders on the new tier, and record refuses the old model. S14S55 VERIFIED

Watch outThe loop cap and the escalation both default to 2, so the second failed review round raises G4 (the user must approve another loop) at the same moment coding moves to routine. S42S12 INFERRED from the two defaults; not run end to end for this guide.

Context budget

packet estimates what it hands the unit (packet, rules file, node card and input files, about 4 characters per token) and returns it as handedTokens. Over a quarter of the tier's context window (profile contextWindow.<tier>, default 200,000) it adds a contextWarning. The packet also tells units to send long command output to <ticket>/logs/ and search it. S56S5S57S58 VERIFIED

Contracts that describe the project (configuration)

These contracts are written once per project or per harness release. They decide which nodes exist for a ticket, which rules each node judges, which model each tier uses, and what instructions a unit gets. The driver reads them on every command and validates each file against its JSON Schema on load, with a bundled validator (or jsonschema when it is installed). S59S60 VERIFIED

How enforcement is labelled: driver = refused at runtime when wrong; partial = some fields checked; none = trusted as written. Since rev 3 every configuration contract is driver-enforced.

The rules files follow

  1. One writer per file, one writer per ticket. state.json, decisions.jsonl, STATUS.md and token-usage.md are written only by the driver, under the ticket lock. Artifacts are written by their node's worker (or the controller, inline). Units never touch state. S8S70S10 VERIFIED
  2. Messages are immutable. Packet, rules and result names carry generation and round, so a rerun adds files and never overwrites. The unit record pins the result's sha256. S2S3 VERIFIED
  3. Artifacts are mutable but marked. On invalidation each stale artifact gets a ## SUPERSEDED: line; the rerun replaces the file or writes below that line, and only the live text counts. The approved digest stays in artifactDigests. S16S43S47 VERIFIED
  4. Nothing is deleted. Invalidation changes records and appends a line; superseded rounds stay in the file as history, and packets hand units a live-only copy. S16S30 VERIFIED
  5. Review inputs are copied in. handback copies the exported review to reviews/round-N and logs its digest, so the ticket does not depend on the original file. S83 VERIFIED
  6. The repository is touched only by coding (full) or change (lite), mutability source. Nodes never commit; only kaneki-ship commits, as the project identity, after the user approves the exact request. What ships is pinned by the subject digest and receipt. S12S46S86 VERIFIED
